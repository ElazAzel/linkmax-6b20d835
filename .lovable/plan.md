# Полная готовность + самоизлечение платформы

Цель: закрыть пробелы во всех модулях по фазам и добавить слой отказоустойчивости, чтобы сбои автоматически восстанавливались, а не превращались в поломанный экран у пользователя.

Важно: база проекта сейчас на паузе. План пишем целиком, применяем после её возобновления (Cloud → Overview → Resume). Фазы 1 и 5 частично можно делать без базы.

## Фаза 0. Возобновление и базовый прогон

- Возобновить базу, дождаться здорового статуса.
- Применить отложенную миграцию безопасности (aggregate_usage, complete_daily_quest, upsert_telegram_account).
- Прогнать линтер БД и проверить, что все публичные таблицы имеют GRANT + RLS.
- Составить отчёт «что реально ломается» по каждой вкладке дашборда (Editor, Leads/CRM, Bookings, Insights, Offers, Automations, Zones, Settings, Admin).

## Фаза 1. Устойчивость фронтенда (авто-ретраи и деградация)

- Единая политика React Query: retry с экспоненциальной задержкой, `staleTime`, отключение retry для 4xx.
- Глобальный перехват ошибок сети: при недоступности бэкенда показываем баннер «работаем в офлайн-режиме» вместо пустых экранов.
- Локальный кеш последних данных (страницы, лиды, настройки) с восстановлением после возврата сети; черновики редактора уже кешируются — расширить на настройки внешнего вида.
- Гранулярные ErrorBoundary на каждую вкладку дашборда и на каждый блок публичной страницы: падение одного блока не убивает страницу, показывается компактный fallback + кнопка «повторить».
- Скелетоны и пустые состояния везде, где сейчас возможен «белый экран».

## Фаза 2. Самовосстановление задач на бэкенде

- Универсальная таблица `job_queue` (тип задачи, payload, попытки, next_retry_at, статус, last_error) + RLS только для service_role.
- Обёртка в `_shared` для функций-воркеров: при ошибке задача не теряется, а ставится на повтор с backoff и лимитом попыток; после лимита — в «мёртвую очередь» с алертом.
- Перевод на очередь критичных цепочек: письма (send-email, send-event-confirmation, send-attendee-email), уведомления (process-notifications, send-*-notification), вебхуки платежей (payments-webhook, robokassa-webhook), индексация (notify-indexnow, google-search-console-submit), автоматизации (process-crm-automations, run-zone-automations).
- Идемпотентность вебхуков: таблица обработанных внешних событий, повторный вебхук не создаёт дубли платежей/лидов.
- Cron-воркер `process-job-queue` (каждые 1–5 минут), защищённый CRON_SECRET.

## Фаза 3. Мониторинг и алерты

- Расширить `health-check`: база, storage, ключевые RPC, свежесть cron-задач, размер мёртвой очереди, ошибки за последний час.
- Таблица `system_health_checks` с историей прогонов; cron-функция `run-health-monitor` пишет результат.
- Алерты в Telegram админу при: недоступности базы, росте мёртвой очереди, падении вебхуков платежей, ошибках публикации страниц.
- Вкладка «Health» в админке: статус подсистем, последние инциденты, кнопка «повторить неудачные задачи».

## Фаза 4. Функциональные пробелы по модулям

Последовательно, по одному вертикальному срезу за раз (схема → RPC/функция → UI → тест):

1. Редактор и публикация: блоки, стили, тема, публикация, SEO-индексация.
2. CRM и лиды: pipelines, стадии, уведомления, экспорт.
3. Бронирования и события: слоты, staff, напоминания, билеты.
4. Платежи и биллинг: Paddle/Robokassa, лимиты тарифов, апгрейды, чеки.
5. Зоны (B2B) и автоматизации.
6. Админка, аналитика, MCP-инструменты.

Для каждого — короткий чек-лист приёмки: сценарий владельца, сценарий постороннего (RLS), сценарий анонимного посетителя.

## Фаза 5. Автотесты-стражи

- Smoke-набор Playwright: главная, /auth, публичная страница, редактор с добавлением блока, отправка лида, регистрация на событие.
- Unit-тесты на очередь задач, идемпотентность вебхуков и политику ретраев.
- RLS-тесты владелец/не-владелец для новых и критичных таблиц.
- Прогон smoke на каждый PR, полные наборы — ночью; при падении — понятный артефакт и команда для воспроизведения.

## Технические детали

- Ретраи фронта: `QueryClient` defaultOptions, `retry: (count, err) => count < 3 && !is4xx(err)`, задержка `min(1000 * 2^count, 15000)`.
- Очередь: `SELECT ... FOR UPDATE SKIP LOCKED` в воркере, чтобы параллельные запуски не брали одну задачу.
- Все новые таблицы: `CREATE TABLE` → `GRANT` → `ENABLE ROW LEVEL SECURITY` → политики; для служебных таблиц только `service_role`.
- Валидация времени/данных — триггерами, не CHECK-констрейнтами.
- Алерты используют существующий TELEGRAM_BOT_TOKEN и CRON_SECRET; новые секреты не требуются.

## Порядок выполнения

Фаза 0 → 1 → 2 → 3 → 4 (по модулям) → 5. После каждой фазы — прогон сборки, тестов и линтера БД, короткий отчёт что починено и что осталось.
