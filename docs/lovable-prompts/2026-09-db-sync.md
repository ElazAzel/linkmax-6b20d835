ШАГ 3. Проверить утечку секретов страниц.
Миграция 20260701031038 выдала роли authenticated SELECT на всю таблицу public.pages. Если SELECT-политика RLS пропускает чужие опубликованные страницы, любой залогиненный пользователь может прочитать webhook_secret, webhook_url, contact_* и integrations чужих страниц.
Проверь:
  SELECT grantee, privilege_type FROM information_schema.role_table_grants
  WHERE table_schema='public' AND table_name='pages' AND grantee='authenticated';
  SELECT policyname, cmd, roles, qual FROM pg_policies WHERE schemaname='public' AND tablename='pages';
Если authenticated имеет табличный SELECT и есть SELECT-политика, пропускающая строки с user_id <> auth.uid():
  - закрой: REVOKE SELECT ON public.pages FROM authenticated; затем GRANT SELECT (<все колонки, КРОМЕ webhook_url, webhook_secret>) ON public.pages TO authenticated;
  - владелец получает секреты через get_my_full_page / get_my_full_page_by_id (SECURITY DEFINER) — код уже так делает.
  - ВАЖНО: прошлый такой REVOKE (20260620131736) сломал запросы, поэтому после изменения проверь в приложении: вход, открытие редактора, автосохранение, публикация, «Мои страницы», настройки страницы, публичная страница. Если что-то падает — откати GRANT SELECT ON public.pages TO authenticated и опиши, какой запрос упал.

ШАГ 4. Атомарное зачисление в кошелёк.

Перед созданием индекса проверь, нет ли уже дублей internal_ref, и опиши их в отчёте (не удаляй).

## Что проверить после Lovable (вручную, 10 минут)

1. Публичная страница с блоком записи → выбрать слот → записаться. Ожидаемо: запись создаётся, ссылка «управлять записью» открывается.
